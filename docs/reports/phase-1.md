### 2.1 Layer: real implementations vs ENOSYS

Real (tested): `rand48` family (bit-identical to glibc, golden values generated with glibc), `sysconf`, `getuid`/`geteuid`/`getpwuid`, `uname`, `gethostname`, `readlink`, `realpath`, `lstat`, two-argument `mkdir`, `fsync`, `flock`, `select` as a sleep, `times`, `mmap`/`munmap` (read-only, shared read-write, private, anonymous, any offset), `posix_spawn[p]`, `waitpid`, `wait`, `getppid`, `signal` for the UCRT signals, `inet_ntoa`, `hton*`/`ntoh*`, `strcasestr`, `fseek`/`ftell` → 64-bit.

ENOSYS + message (`manifests/enosys.txt`): sockets and `gethostby*`, `select` on descriptors, `fcntl`, `popen`/`pclose`/`system`, `setitimer`, `pause`.

### 3.2 Runtime comparison with Linux (same tag)

Test data: a synthetic dataset generated by the Linux build (`3dcalc -a jRandomDataset:32,32,16,6`), stored as `.BRIK`, `.nii`, `.nii.gz` and `.BRIK.gz`. Both platforms ran with an isolated `HOME` (the user's `~/.afnirc` sets `AFNI_COMPRESSOR=GZIP` and changed the reference output before isolation).

| Check | Result |
|---|---|
| `3dinfo` on `.BRIK`, `.nii`, `.nii.gz`, `.BRIK.gz` | identical to Linux after normalising absolute paths |
| `3dcalc -a rnd+orig -b rnd.nii.gz -expr 'a*b/100+sqrt(abs(a))'` (BRIK out) | `.BRIK` **byte-identical** |
| `3dcalc -expr 'sin(a)*exp(-abs(a)/50)+log(1+abs(a))'` (NIfTI out) | data and 348-byte header identical |
| `3dcalc -datum short -expr 'step(a)*a'` (`.nii.gz` out) | data and header identical (the gzip stream differs in the OS byte only) |
| `3dTstat -mean -stdev -max` (BRIK) | `.BRIK` byte-identical |
| `3dTstat -median` (`.nii.gz`) | data identical |

| `3dinfo '3dcalc( -a rnd+orig -expr 2*a )'` (patch 0002, `posix_spawnp`) | works, same output |

The transcendental functions came out bit-identical, but under wine they are computed by wine's implementation of `ucrtbase`. This must be repeated on real Windows.

## 4. Checks requested in the decisions

### 4.1 busybox-w32 `sh` for `popen`/`system` (D8)

`busybox64u.exe` 1.38.0 (frippery.org, sha256 `6e263d154d8548d1eb936f65d1d8312c80df31c45974e48d6335e4dcc0f4f34c`), under wine:

| Command | Result |
|---|---|
| `sh -c "gzip -dc 'my data.BRIK.gz'"` (AFNI's `COMPRESS_unprogram` form, file name with a space) | correct output; `gzip` is a built-in applet, no `gzip.exe` needed |
| same with `'Z:/opt/bb/my data.BRIK.gz'` and `'Z:\opt\bb\my data.BRIK.gz'` | correct |
| `sh -c "gzip -c > 'out.gz'" < file` (write pipe form) | correct |
| `sh -c "rd < pts.txt"` with a native test program found through `PATH` | correct (stdin redirection to a native `.exe`) |
| `sh -c "qhull -i -Pp < pts.txt"` | redirection and `PATH` lookup work; **`qhull` built from upstream `src/qhulldir` fails on Win64**: `QH6084 qhull internal error (qh_meminit): sizeof(void*) 8 > sizeof(ptr_intT) 4`. `ptr_intT` is `long`, 4 bytes on Windows. Upstream uses a system qhull by default (`USE_SYSTEM_QHULL=ON`); MSYS2 has `mingw-w64-ucrt-x86_64-qhull`. |
| `sh -c "echo x >& /dev/null"` (tcsh-style redirection used by AFNI) | accepted by busybox `sh` |
| `command -v tcsh` | not available: `cs_playsound.c` and `kill_sound_players` call `tcsh -c` |

Conclusion: busybox `sh` handles the AFNI command forms checked. The external tools themselves (qhull, cjpeg/djpeg, curl, …) still have to be shipped or found on `PATH`.

### 4.2 Global variables exported from `libmri.dll` (D5)

- Programs reference 9–10 data symbols of `libmri` directly, e.g. `3dcalc`: `DBG_fp DBG_hist DBG_num DBG_rout DBG_stoff DBG_trace hist_status last_status`; `3dTstat` also `g_thd_maker_allow_1brick`. No `dllimport` is used upstream; MinGW auto-import with runtime pseudo-relocations resolves them.
- Behavioural check: `3dcalc -TRACE` sets `DBG_trace=2` in the program; the trace lines printed by functions inside `libmri.dll` (`THD_open_dataset`, `THD_load_datablock`, `EDIT_empty_copy`, …) appear, and the call depth (`DBG_num`, incremented in the exe and in the DLL) is continuous across the boundary. Auto-import works for these globals.
- The Windows trace is shorter than the Linux one (372 vs 406 entries). The difference is not the DLL: `THD_getpathprogs` splits `PATH` at `:` (`thd_getpathprogs.c`), so on Windows it sees fewer directories (section 5).

### 4.3 64-bit offsets and LLP64 diagnostics (D11)

- `fseek`/`ftell` map to `_fseeki64`/`_ftelli64` (object-like macros, identical to the ones `nifti/znzlib/znzlib.h` already defines for `_WIN32`, so there is no redefinition warning). `sizeof(off_t)` and `st_size` are 8 with `_FILE_OFFSET_BITS=64` (unit test).
- `-Wshorten-64-to-32` exists only in clang; GCC has no such option. I used GCC `-Wconversion` filtered to conversions from a 64-bit type to `long`/`unsigned long` (narrowing that exists only on Windows, since `long` is 64-bit on Linux), plus `-Wpointer-to-int-cast` and `-Wint-to-pointer-cast`. Scope: all 362 translation units of `libmri` and `3dinfo`/`3dcalc`/`3dTstat`.

| Location | Code | Assessment |
|---|---|---|
| `suma_datasets.c:14147,14181` | `len = THD_filesize(fname)` into `long` | wrong size for files > 2 GiB (SUMA NIML datasets) |
| `suma_utils.c:1403` | `NewName->Size = THD_filesize(...)` | same, size only reported |
| `thd_atr.c:281` | `fsize = NI_filesize(headername)` | `.HEAD` files, never > 2 GiB |
| `afni_logger.c:62` | `THD_filesize(fn) > 100000000` | log file size check |
| `mri_dicom_hdr.c` (13 sites) | DICOM element lengths `size_t` → `long` | element lengths < 2 GiB by format |
| `thd_filestuff.c:558,572` | `strlen` → `long` | harmless |
| `niml/niml_uuid.c:67` | `tv.tv_usec = (long) buf` | address used as entropy, truncation harmless |
| `suma_utils.c:2085` | `N = (int)p` | pointer → `int` |
| `mri_dicom_hdr.c:1990` | `(unsigned char *) offset` | 32-bit offset round-tripped through a pointer, harmless |

No finding affects the dataset read/write path of `3dinfo`/`3dcalc`/`3dTstat`. The other required programs were not part of this diagnostic.

### 4.4 `whereami` runtime files (D10)

- `AFNI_atlas_spaces.niml` from `src/`. The Make build installs it (`Makefile.INCLUDE:2310`); **upstream CMake does not install it**. It must be added to the release.
- The atlas datasets referenced there (17: `MNI_Glasser_HCP_v1.0.nii.gz`, `BN_Atlas_246_1mm.nii.gz`, `MNI_caez_*`, `TT_caez_*`, `HaskinsPeds_NL_atlas1.01+tlrc`, `FS.afni.*`, `Brodmann*`, `Julich_*`, plus `TTatlas` used by `get_atlas_dirname`) are not in the upstream repository. They come from AFNI's separate atlas distribution (CMake `COMP_ATLASES` downloads it with datalad) and have their own licences, so whether they can go into our release is a separate question.
- Search path: `AFNI_ATLAS_PATH`, then `AFNI_PLUGINPATH`, `AFNI_PLUGIN_PATH`, `PATH` (`thd_ttatlas_query.c:640`), split at `:` (`thd_ttatlas_query.c:618`). With `whereami -show_atlases` under wine, `AFNI_ATLAS_PATH=Z:/…` works only because the remainder after `Z:` is resolved on the current drive, which is also `Z:` under wine. On Windows a value like `C:/afni/atlases` works only while the current drive is `C:`.
- Optional: the linkrbrain query runs `curl` through `system()` (`thd_ttatlas_query.c:1738`).

### 4.5 `alarm`

`compat/CMakeLists.txt` compiles a test program that calls `alarm()`. With the toolchain (`--wrap=alarm`) the link fails, as intended; without it, the configure step aborts with "alarm() links (MinGW libmingwex stub)". Verified both ways.

## 5. Findings for phase 2

1. **`PATH`-like lists split at `:`** — `thd_getpathprogs.c` (finding executables such as `gzip`), `get_atlas_dirname`/`get_env_atlas_path` (atlases), probably more. Windows paths contain `X:`. This is not covered by the spec's "paths and environment" row and needs a decision (Q1 below).
2. `TMPDIR`/`/tmp`: `thd_mastery.c:507-508` uses `TMPDIR` or `/tmp` as session directory for `3dcalc(...)`; `mri_purger.c:28` uses `TMPDIR`. Works under wine only because wine maps `/tmp`.
3. `HOME`: `afni_logger.c:49,91`, `afni_environ.c:168`, `thd_filestuff.c:232` use `getenv("HOME")`, which is usually unset on Windows (logging and `~/.afnirc` silently disabled).
4. `system()` is used even for small things: a misspelled option in `3dinfo` prints the ENOSYS message because the option suggestion runs `3dinfo -help` through `system()`.
5. `3dQwarp` installs a `SIGQUIT` handler (`mri_nwarp.c:8095`, not covered by patch 0006). With D7 this prints "signal(3) is not supported on Windows" on every run.
6. Files mapped with `mmap` cannot be deleted or truncated on Windows while mapped (datasets larger than `MMAP_THRESHOLD` are mapped read-only). Overwriting an input dataset in place may fail where it works on Linux. Not tested yet.

## 6. Deviations from the spec and from the decisions

| What | Why |
|---|---|
| `afni_compat` is a DLL, plus a tiny static library `afni_compat_binmode` | D5a (asked and confirmed); the static part only defines `_fmode` |
| `binmode.o` is not used | In `ucrt64-crt 13.0.0` the file is empty (`nm` shows no symbols) and `_get_fmode()` stays `_O_TEXT`. The first run read only 656 of 393 216 bytes of a `.BRIK` (text mode stops at byte `0x1A`). Whether MSYS2's `binmode.o` is also empty is unknown; ours works either way |
| stdin/stdout/stderr in binary mode | To match Linux (no LF→CRLF translation). Before the change, `3dinfo` output had CRLF line ends |
| gifti through `cmake/gifti/` instead of `FETCHCONTENT_SOURCE_DIR_GIFTI_CLIB=src/gifti` | D4a; the in-tree CMakeLists downloads nifti_clib master into the source tree |
| `LINUX` is not defined | Upstream defines it only for Linux; the Windows build takes the generic branches. As a consequence `mallopt` (`machdep.c:39`) and `statfs` (`thd_filestuff.c:689`) are not compiled, and `mallopt` is not declared yet (listed in the allowlist for when it is needed) |
| `READ_WRITE_64` defined in `afni_compat.h` | Upstream CMake passes `-DREAD_WRITE_64` on Linux and macOS; without it `f2c/rawio.h` declares `read`/`write` with conflicting types |
| `_WINSOCKAPI_` defined in `afni_compat.h`; `SOCKET`/`INVALID_SOCKET` provided | `<windows.h>` would otherwise include `winsock.h`, whose `fd_set`/`select` conflict with the POSIX ones. Upstream's `mri_dicom_hdr.h` includes `winsock.h` under `_WIN32` only for the `SOCKET` type |
| empty `sys/ioctl.h`, `net/if.h` | `niml_uuid.c:283-284` includes them unconditionally but uses them only under `LINUX`. Nothing is declared |
| `pause()` added as ENOSYS | Referenced by the f2c runtime (`s_paus.c`, Fortran `PAUSE`), which is part of `libf2c.dll` |
| `--require-defined=afni_compat_runtime` on every consumer | The PE linker drops a DLL import when no symbol is used, so the DLL constructor (binary mode) would not run in such programs |

## 7. Corrections to the phase 0 report

- Section 9.5 / risk 4: `znzlib` is not limited to 32-bit offsets on Windows — `znzlib.h` defines `znz_off_t` as `long long` and maps `fseek`/`ftell` to `_fseeki64`/`_ftelli64` under `_WIN32`.
- The `_WIN32` branch with `long hFile = _findfirst(...)` (`mri_dicom_hdr.c:12186`) is inside `#if 0` (`mri_dicom_hdr.c:12179`) and is not compiled.
- `cs_playsound.c` needs a patch (0005), see section 2.2.
- `fork` sites: the static-library view in the phase 0 report undercounted what a DLL must link; with `libmri.dll` every object must link.

## 8. Questions

- **Q1.** `PATH`-like variables are split at `:` in several places (section 5.1). Options: (a) patch the splitting functions to use `;` on Windows; (b) document that these variables must use `/c/...`-style paths (MSYS2 style) and convert in the layer's `getenv`; (c) something else.
- **Q2.** Confirm binary mode for stdin/stdout/stderr (section 6).
- **Q3.** Phase 1 acceptance on real Windows: run `tools/build.py` in MSYS2 UCRT64 on your machine, or wait for the CI runner in phase 4?

### Licence finding

The spec (section 6) says AFNI is mostly GPL. Upstream `LICENSE.txt` says otherwise: AFNI is a US Government work in the public domain, with listed third-party exceptions (MIT, BSD, LGPL-2, GPL-2.0, GPL-2.0-or-later, GPL-3.0, GPL-3.0-or-later). Relevant for us:

- `src/3DEdge` is GPL-3.0 and is linked into `libmri.dll`, so the distributed binaries are effectively GPL-3.0. That matches the GPL-3.0 licence of this repository.
- Parts under plain "GNU GPL 2.0" (which may be GPL-2.0-only) are `src/mpegtoppm_dir` and `src/SUMA/SUMA_{coarsen.c,gts.c,gts.h}`. Neither is built in the current scope. If SUMA is added later, combining them with GPL-3.0 code (3DEdge, `afni_compat`) has to be checked.
